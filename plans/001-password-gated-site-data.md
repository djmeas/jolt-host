## Why

An uploaded HTML/ZIP site cannot persist shared data across browsers today. Give each **existing static upload** an optional, private SQLite file and a versioned JSON-record API; do not run uploaded server code or expose raw SQL/DB files. For password-protected, data-enabled sites, an unlock URL grants **view and API read only**, whereas explicitly entering the password grants **view plus full CRUD over that site's records**. Neither credential grants upload management (replace/delete/password settings); existing account/owner-token rules continue to govern that. A site password is a shared data-admin credential: all holders can change everyone's records; per-visitor private data and audit identity are not provided.

## Contract to implement (no open-ended design choices)

### 1. Origin and URL boundary — required before data auth

- Configure `JOLT_APP_ORIGIN` (full scheme/host/port), `JOLT_SITE_BASE_ORIGIN` (full scheme/base-domain/port, without wildcard), and `JOLT_DATA_SESSION_SECRET`; require a strong `JOLT_VIEW_SECRET` as well when data is enabled. Canonical site URL is `<slug>` prefixed to the base origin's hostname. The hosted origin must use a **different registrable domain** from the app (e.g. app `https://host.example.com`, hosted base `https://sites.example.net`; dev: `http://sites.localhost:3000`). Use a Public Suffix List parser, not string suffix comparisons, to reject same-site production configurations. Wildcard DNS and TLS must route `*.sites.example.net` to the same Node service/proxy; document exact proxy/TLS requirements. Do not assume a path prefix or sibling subdomain of the app host is an isolation boundary. Production data feature MUST fail closed when hosted-origin config, signing secrets, or HTTPS is missing. Never construct redirects from an arbitrary incoming `Host` header.
- Canonical public URL: `https://<slug>.<configured-hosted-suffix>/` (dev uses configured scheme/port). Route that host to **only** site static HTML/assets and `/_jolt/data/...`; return 404 for app `/`, `/api/*`, `/admin/*`, `/dashboard`, unrelated slugs, and any unrecognized service path. App-origin legacy `/view/<slug>` and asset links redirect to the matching hosted origin; they must never serve executable uploaded content on the app origin. Preserve `?unlock=` (view only) across redirects; strip `owner_token`, `password`, and other unrecognized query credentials instead of forwarding them into uploaded JS. Strip tokens from referrers using `Referrer-Policy: no-referrer` on unlock-related responses. Prevent traversal/symlink escapes using a path-component-aware containment check, not the current `filePath.startsWith(baseDir)` prefix check.
- Update all link producers in the current-state list: creation/replacement responses, admin/user upload lists, dashboard, result, update, delete pages. Return `owner_token` **only** in the one-time JSON response; remove `url_with_owner_token` everywhere (response, docs/tests). Existing saved `/view` URLs remain usable via redirects. Include `url_with_unlock` on the new hosted origin. App login/admin cookies remain host-only on the app host; site-hosted responses must not mint app upload sessions. Never use permissive credentialed CORS between the two origins.

### 2. Opt-in site database and lifecycle

- Add `uploads.data_enabled INTEGER NOT NULL DEFAULT 0` using existing additive migration convention. Data can be enabled only while the upload exists, is unexpired, and has a password. Add `PUT /api/uploads/[slug]/data` with JSON `{ "enabled": true|false }` returning `{ "slug": string, "data_enabled": boolean }` (200), using the same site-ownership authorization as content replacement (`authorizeContentUpdate`, with the established registered-only/API-token rules); a general upload token or view/data session is not ownership proof. Enabling without a password returns 409. Expose `data_enabled` in management list responses and a small enable/disable control in dashboard; show that a password is required. No additional provisioning, backend-code upload, or visitor account flow.
- Database path: `data/sites/<immutable-upload-id>.sqlite`, or `test/tmp-data/sites/<id>.sqlite` under test mode; create lazily on first authorized write, not on upload. Never place it, `-wal`/`-shm`, or backups in `storage`, `public`, Nuxt public output, or ZIP content. Derive filename solely from the validated row's UUID. Server-controlled schema, e.g. `items(collection TEXT, id TEXT, value_json TEXT, created_at TEXT, updated_at TEXT, PRIMARY KEY(collection,id))` plus list index. Only accept an object as `value`, persist UTF-8 JSON, use bound parameters, and forbid supplied SQL/schema statements. Open/close connections on each operation (bounded handles); use SQLite transactions for quota checks + mutations and a finite busy timeout. Any WAL-enabled backup must use SQLite's consistent backup mechanism, not copy only the `.sqlite` file.
- Defaults/limits: collection matches `^[a-z][a-z0-9_-]{0,39}$`; at most 10 collections with records, 1,000 records/site, 4 KiB serialized JSON/record, and 1 MiB total serialized payload/site; quota checks are transactional and include replacements. Bound incoming request bodies to 8 KiB **before** full JSON parsing, rather than reading unlimited bodies and checking afterward. GET of an empty or as-yet-uncreated collection returns `{ "items": [], "next_offset": null }` without creating a DB file. List defaults to 50, max 100, with nonnegative `offset`, deterministic `(created_at,id)` ordering and `next_offset` or `null`. IDs are server-generated UUIDs. Return 400 invalid input, 401 missing credentials (including unauthenticated GET), 403 view-only session attempting a write, 404 missing/expired/disabled site or record, 413 too-large payload, 429 rate limit, 409 quota conflict. Use `Cache-Control: no-store` on all data/auth responses. Separate bounded in-memory limits: 5 failed password attempts/IP/site per 15 minutes and 50/site per 15 minutes; 60 writes/data-session/site per minute and 120/site per minute. Set `Retry-After` on 429. Obtain IP only from a trusted proxy or the socket, never an arbitrary forwarded header. Document that multi-instance deployment needs a shared/edge limiter.
- Code replacement leaves the site's DB untouched. Disabling data retains records but blocks both reads and writes; clearing the password disables data and revokes write sessions, preserving records until deletion. Re-enabling after a new password reveals the original records to the new password holders; explain this in the UI/docs. All owner/admin/expiration deletion paths must remove the DB and sidecars after rejecting further access; coordinate open handles, and reconcile orphan files after crashes/races. Site deletion and expiration return 404 on subsequent reads/writes.

### 3. Viewer versus password-holder authorization

- `GET /_jolt/data/v1/collections/<collection>/items?limit=&offset=`: only when data is enabled and the site is unexpired; authorize existing site **view cookie**, whether earned through password or `?unlock=`, or a valid data-admin cookie. Unauthenticated requests return 401 JSON with `login_url` set to `/_jolt/data/login`. Return `{ "items": [{ "id", "value", "created_at", "updated_at" }], "next_offset": number|null }`. View-only unlock grants **read**, not writes.
- `POST /_jolt/data/v1/collections/<collection>/items` body `{ "value": {...} }` returns the item (201); `PATCH /_jolt/data/v1/collections/<collection>/items/<id>` body `{ "value": {...} }` replaces the full JSON value (200); `DELETE .../<id>` returns 204. All mutations require a valid **data-admin** session issued only by a Jolt-owned password form POST on the hosted origin; a view cookie, unlock URL, site owner token, app admin/user session, or API upload token never authorizes these endpoints. No public writes; public unprotected uploads cannot enable data in this plan. Confirm host-derived site identity on every request and scope both cookie and DB lookup to its immutable ID. Reject cross-site host/slug mismatches.
- GET `/_jolt/data/login` displays Jolt-owned password form even for visitors who already have view access; POST validates the password (in form body, never query), then sets both view cookie and distinct host-only `jolt_data` cookie; redirect with 303 to the site's root. Make the normal site password POST-unlock grant both cookies **only** when data-enabled. `?unlock=` and legacy GET `?password=` MUST NOT mint data-admin cookies (remove query-password support and redirect to the safe form). Uploaded HTML/JS must not see the password form or receive the password/session in JSON. Cookies: `Secure` in production, `HttpOnly`, `SameSite=Strict`, no `Domain`, path restricted to data API for data-admin; signing secret separate from view secret, required in production, fixed short TTL (24 hours). HMAC/signature includes immutable site ID, expiry, and current password-hash version; verify constant-time and check current upload status/hash on every request so all password changes immediately revoke data-admin cookies. View/unlock credentials keep their existing **view-only** semantics/expiry; do not silently promote them. A logged-in holder can call same-origin `fetch` without JS reading the cookie.
- Require exact hosted `Origin` and suitable content type on every state-changing data request, data login **and normal password-form POST when it grants data-admin access**; reject missing/mismatched origin for cookie-authenticated mutations and disable cross-origin credentialed CORS. A malicious script within the authorized site can still act as the password holder: `HttpOnly` prevents token reading, not same-origin requests. Document this trust limit. Never render stored record text as HTML in the example.
